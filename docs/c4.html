Where authority comes from

Level 1 states which plane serves each group. This states where their authority is minted and where it is spent — they are different questions, and the second is the one that decides whether a design is safe. A customer browser never meets the control plane; staff authenticate on the platform connection, but staff reach into a tenant is a grant evaluated in the plane, because being staff is not access.

Why customer traffic terminating in the plane is also a billing property

  • all session, serving and inference cost sits in the plane
  • under BYOA that is the customer's own AWS bill
  • 1CloudHub never carries per-customer serving cost
  • UsageRecord ships up with no UserId — per-user analytics is impossible by construction

What splits, and into what

  • web → admin console (control) + tenant web app (data)
  • API → control-plane.openapi.yaml (control) + capability & foundation (data)
  • database → control schema + tenant schema, one cluster per residency region (G185)
  • roles → control_rw · tenant_rw · tenant_migrate — control_ro retired (G185)

Why do it before BYOA

  • under BYOA the split is physical — separate AWS accounts
  • the data plane pulls packs and policy over signed HTTPS
  • which IS one code path in both topologies — control_ro was not
  • a grant is enforcement; review is not a mechanism

What C1 buys, stated as a feature rather than a constraint: the entitlement lease is verified offline and drawn down locally, so a control-plane outage stays invisible to the customer until the lease expires. Metering is fire-and-forget and must survive the control plane being down — buffered and replayed with its original sequence numbers. That property is only reachable if nothing on the hot path calls upward, which is why C1 is written as a hard requirement rather than a preference.

The not-built marks — and two corrections to how they are usually described

The hatch mark is the most useful thing in the bundle: it is a drawn screen admitting, in place, that what it is drawing does not exist. But the shorthand for it is wrong in two ways, and both matter to anyone counting.

⚠️ It is 90 marks, not 98

grep -o 'data-nb=' design/routes/*.html | wc -l returns 98 — and 8 of those are the reproduction commands matching themselves. Several route files say so in their own prose. The real mark count is grep -oh 'data-nb="not built"' design/routes/*.html | wc -l → 90, of which 86 are on the five route files and 4 on the contact sheet. This is grep -c-versus-grep -o in the wild, and it has shipped a wrong count here before.

⚠️ data-nb does NOT name the decision

Its value is the constant string not built — one spelling, 90 times. It exists so the hatch carries a printed word that survives greyscale (design/system/tokens.css:958, .nb::after{content:attr(data-nb)}). The refusing authority lives in a separate <span class="nbwhy"> — grep -o 'class="nbwhy"' design/routes/*.html | wc -l → 84. 90 against 84, and per file they do not correspond either (entry 23/25, reports 9/14, close 26/19): the mark and the reason are not paired one-to-one, so "each mark names the decision that refused it" is not a claim this tree supports.

What a reason looks like when it is there — the authority first, in bold, then prose, then usually a reproducible grep: design/routes/close.html:767 — "G155 not applied, and no wire carries this row." · design/routes/entry.html:826 — "A shared session has nowhere to live." · design/routes/entry.html:539 — "PRODUCT.md — never a named customer or logo." · design/routes/finding.html:889 — "DP-4 — the residue-to-exception join does…". So the authority is a G### ruling, a PRODUCT.md rule, a DP-# defect, or a bare statement that the model has no such noun.
