Every location it holds points at a database row. Audit trail

The record for the id the status bar is printing. Read-only: every control that changes something is absent here rather than disabled.

The id on every protected surface resolves here — to the run behind it, the decisions taken on it, and who took them. An assurance reader signs in read-only through the customer’s own IdP and reads the register and the reports as well, because a trail with no access to what it describes is a list of hashes. Ask is not among them: every turn it takes prints what it cost, on the same usage stream that becomes the invoice, so it spends the tenant’s plan and an assurance reader does not get it. What this source carries, and how we tell one document from another

One source carries several document types — an SFTP drop holds statements and advices in the same folder; one intake address receives invoices and remittances. The type is not a property of the source, so it cannot be chosen once here. What identifies a document is the pair: this source, and a pattern within it — a prefix or subfolder, a filename pattern, a subject line, or the sender. Each pair names one document type, and a delivery matching no pair is parked as unclassified rather than guessed into the nearest type.

Specified, not built. Today a source inherits its types from the installed pack, which holds only while a source carries exactly one of them. The pair is the unique identifier the model needs and does not have.

Editing an installed pack

Nothing in the table opens, and three of a pack’s five parts have to be changeable. Tenant-editable: the variables (a bucket moves, a path changes), the SOPs, and the tolerances a rule reads. Pack-owned: the document types, the rules themselves and the matching arity — changing those is a new pack version, and it comes from 1CloudHub. Every tenant change is an overlay carrying the pack version it was written against, so an upgrade can say which overlays still apply instead of dropping them. All of it effective on the next run, never mid-period.

Specified, not built. The overlay does not exist in the model, so neither does a control that would write one — and the 2 SOP overlays the table reports against the bank pack states the shape of the thing, not a record of something a control produced.
Documents that were never digital

A scanned statement or a handwritten remittance advice reaches the same pipeline as a machine-produced file, and it does not arrive as fields. Textract reads the page, then the values it read have to be mapped to the document type’s fields — the same amount can be called Amount, Total Due or nothing at all on three suppliers’ paper. Two things follow from that, and the surface has neither.

Field mapping, per source and document type

What the page calls a field, against what the type calls it. It hangs off the source-and-pattern pair above, not off the source — one supplier’s layout is not another’s. Until it exists, consistency across a document type rests on the pack’s definitions matching the paper, which is an assumption, not a control.

Specified, not built. The pair it depends on does not exist either, so this is the second thing blocked by it.
A floor per document type — and who proposes it

One floor for the tenant is too blunt once OCR is in the mix: a handwritten advice cannot be held to the confidence a generated PDF reaches, and holding it there parks every field on it. The floor belongs to the document type, not the tenant.

Undecided, and it needs deciding before this is drawn: either the mapping and the floor are declared before the first run, and nothing extracts until they are — or the first run is treated as a calibration, the system proposes both from what it read, and an admin accepts them before any period rests on them. The second is kinder and costs a run nobody can close; the first is honest and stalls onboarding at exactly the point a customer is watching.

Not decided. Recording it as an open decision rather than drawing one of the two, because the choice changes what onboarding is, not just what this pane shows.

Tag policy · C10

The cost-centre vocabulary is theirs — they own the names — and what the meter does with them is ours. One key is nominated to drive chargeback, and everything downstream depends on that one choice.

Agreeing the vocabulary, and nominating the key

Neither exists. The vocabulary is a conversation between the customer and delivery with no surface; nominating the chargeback key is done from the 1CloudHub side, because it changes how usage is reported rather than what this tenant sees.

And this one cannot be repaired late. Every usage record emitted before the agreement carries no tag, and the records cannot be re-tagged — they are the same records the invoice rests on. A tenant starts hosted and escalates to its own account when a security review requires it. The escalation is commercial and security, not technical, and it is run by 1CloudHub rather than from this pane.

Escalating hosted to BYOA

The full BYOA provisioning runs again in the customer’s account, then everything migrates — documents, runs, resolutions, approvals and the audit trail. Not a subset: a regulated customer will not accept a lost history, and a partial migration is the same thing wearing a better word. A seed run reconciles counts against the old plane before anything is torn down, and the old stack is then decommissioned so no duplicate of regulated data is left in an account we may no longer be provisioned in.

The new plane is authoritative from cutover and the old one is read-only immediately, so there is never a moment when two planes both accept work. The cost of that rule is that a failed verification cannot be fixed by falling back — it is fixed by re-migrating forward, by 1CloudHub delivery.

Specified, not built. The migration, the count reconciliation and the cutover are delivery procedures with no surface on either side. This tenant’s mode is read here and cannot be changed here.
