Where a refusal is drawn instead

A page like this is what the server returns when there is no application to draw into. Inside the product a refusal is never a page: a destination a role does not hold is absent from the navigation, and a control it may not use is drawn with the reason beside it at full ink. Sending someone to a 403 for something the product could have simply not offered is a design failure wearing a status code.

Why the code is on the page

Every failure path in this product emits a code from a closed vocabulary, because under a restrictive telemetry profile the class of an error is the only diagnostic channel that survives. So the code is printed where a person can read it out, and the reference beside it resolves to a record — the run, the act, the request — that support can open without asking them to describe a screen.

What none of these pages do

They do not guess at a cause where two causes look alike, they do not apologise for a control working, and they do not offer a retry that cannot help. The way back is always somewhere that exists — the register, the sign-in route, or the site — never a reload of the thing that just refused.

Illustrative. Six states, drawn on the public shell because that is the shell that survives when the application does not. The 5xx pages are the only ones that apologise, and only because the fault is ours and it cost the reader something.
